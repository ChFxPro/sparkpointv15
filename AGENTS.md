- Public intake (`/intake`) writes to the `intake_submissions` Postgres table and pushes a best-effort item to the
  `SparkPoint Intake Inbox` Monday board (`18399040367`). The board's long-text **Message** column carries the whole
  submission — free text, blank line, then `- Label: value` extras. **Adding a column in Monday's UI does nothing on
  its own:** `pushToMonday` only sends the column ids it is given, which is how the Message column sat empty from
  2026-07-21 until PR #154. Monday truncates a long-text value over 2,000 characters on write, so the composed value
  is capped with a pointer to the Supabase id. The intake validator's field ceilings mirror the `intake_*_len` check
  constraints on the table — keep them in step, or a submission passes validation and then dies on the INSERT as a
  500 instead of returning a 400. The form also carries an off-screen `website` honeypot; a tripped submission is
  answered with a normal-looking success and stored nowhere.

- **The BackPorch** (`/backporch`) is SparkPoint's own feed, built so updates live on the site and Facebook gets photo posts that point home (Meta caps link posts at 2 a month unless paid). Spec and go-live steps: `docs/backporch/SPEC.md`. Posts live in the Supabase table `porch_posts`; only emails in `porch_editors` can write (the project's Auth is shared with other tools, so "signed in" is not enough). `scripts/backporch/bake.mjs` runs in predev/prebuild and bakes published posts into git-ignored `src/data/backporch*.generated.json` and `public/backporch/feed.{xml,json}`; pages render the baked posts first, then refresh live from Supabase. In CI a failed fetch fails the deploy; a missing table bakes zero posts. The homepage band `src/components/backporch/BackPorchBand.tsx` sits directly under the hero and is what the homepage features: it leads with the pinned posts — up to three (`MAX_PINS`), most recently pinned first (`pinned_at`, set by the database trigger; pinning a fourth unpins the one pinned longest ago) — or the newest post when nothing is pinned, then three more. One lead sits beside the title; two or three sit side by side under it. It must stay still (no rotation, badges, or layout shift; hidden when there are no posts). Time-sensitive features (an event, a registration) are pinned posts with a "take off the lists" time. Staff write at `/internal/backporch`, which also makes the Facebook kit (post text plus a 1080×1350 share image with the short address and QR). No tracking parameters anywhere. `deploy.yml` rebuilds every two hours so baked pages catch up; the editor's "Update the site now" calls the `backporch-publish` edge function. Partners are called "neighbors" (phase 2). **Post bodies are blocks** (`porch_posts.blocks`, jsonb): text, photo, gallery, video clip (≤1 minute, uploaded), YouTube/Vimeo, audio, quote, link, place, PDF file, and experiment. Every renderer runs them through `normalizeBlocks()` in `src/lib/porchBlocks.ts` first (known types only, https links, bucket paths, embed ids) — keep it that way; never render HTML from a block. YouTube/Vimeo load nothing until play (privacy promise). The editor's `BlockComposer` turns dropped files into blocks (several photos become a gallery), offers Event/Ask/Photo story/Voice note starters, autosaves to localStorage, and uses the first photo as the cover unless one is chosen. **Experiments** (coded, one-of-a-kind posts) live in `src/experiments/backporch/<id>/` (`meta.ts` + `index.tsx`), start with `npm run porch:experiment <id>`, ship through a PR, each as its own lazy chunk; a post uses one through an Experiment block. They are code in the repo, not uploads, because anything running on the site could reach an editor's session. Sample: `porch-light`. **The Porch Lab** is the testing ground for experimental BackPorch tools, configured in the editor without code: animated text, living backdrop (canvas sunrise/fireflies/ridges, pausable, still under reduced motion), count-up numbers, before & after, scrolly story, timeline, quick poll, and post-level porch reactions, plus frame-breaking: any visual block can be column, wide, or edge-to-edge, and a post can be a *takeover* (its first backdrop/photo block fills the screen under the title, its `presentation.mood` recolours the page, and in the feed it breaks out of the list as a full-width still). Each tool has a stage in `src/lib/porchLab.ts`: `lab` (editor previews and the `/internal/lab` bench only; `publicBlocks()` strips them from the public page), `field` (public, untagged: the "Field test" tag shows only in the editor preview and the lab bench, owner's call 2026-10-20), `released`. Promote by changing the stage, after `RELEASE_CHECKLIST`. Polls and reactions write only through security-definer functions (`porch_vote`, `porch_react`, `porch_poll_results`, `porch_reaction_counts`) keyed by a random per-browser token; their tables have RLS on and no policies. **Link previews:** pasting a link into a Link block fetches that page's own title, description, site, and image (edge function `porch-unfurl`, editors only, SSRF-guarded) and stores a copy of the image in `porch-media`, so the public card (`pb-unfurl`) never requests anything from the other site; the block keeps it as `preview`. With no cover chosen, a post's image is its first photo, or, if it has none, its first link's preview image (`coverFallback()` in `porchBlocks.ts`); on the post page that image opens the link (`linkForImage()`), and the link card below drops its duplicate copy. **Local demos:** `/internal/backporch/demo` and `/internal/lab/demo` run the editor and bench on the baked sample posts with no sign-in and nothing saved; they are routed only under `import.meta.env.DEV`, and the dev server stands in for `porch-unfurl` at `/__dev/porch-unfurl` (`vite.config.mts`, `apply: 'serve'`), saving images to git-ignored `public/assets/backporch/dev-unfurl/`. Posts render through `src/components/backporch/PostView.tsx`, shared by the post page, the editor's full preview, and the bench. **Look:** SparkPoint's palette and type (plum, pink, Manrope; Fraunces only for the BackPorch wordmark, a post's own title on its page, and pull quotes — post titles in lists, section labels, chips, media titles, and Lab tools are Manrope, owner's call 2026-10-20) with warmth borrowed from the Rural Health Field Simulator, for influence rather than a match: cream paper with grain and faint contour terrain, an AI-generated, illustrative "view from the porch" (friends in rocking chairs at sunset over unnamed Blue Ridge ridges; the owner removed Looking Glass Rock because a recognisable-but-wrong landmark read as fake) in three crops, `public/assets/backporch/view-{wide,square,tall}-*.webp`, rendered by `src/components/backporch/PorchView.tsx` (the owner removed the "Illustrative image" label from the homepage band and the `/backporch` header on 2026-10-20; post pages still carry it), which sinks into a deep ridge-dusk "night" (`--bp-night: #1f1b26`, sampled from the image's far ridges) through a multiply wash. ### Supabase edge functions — where they actually live
**`supabase/functions/README.md` is the canonical inventory.** Read it before deploying,
adding, or deleting a function. Kept there rather than duplicated here, because a fact
stated in two places drifts — this section already went stale once.

The short version:

- `supabase/functions/<slug>/` is the **only** path the Supabase CLI reads. Anything under
  `src/` or inside a worktree is not a deploy path.
- This repo deploys two functions: `make-server-393f2b0a` (health + public intake) and
  `rh-ticket-stock` (read-only seat-count proxy for the convening page). A third,
  `backporch-publish` (starts a site rebuild for BackPorch editors), is in the repo but not
  deployed until its `GITHUB_DEPLOY_TOKEN` secret exists.
- **Ship functions from that directory through a PR — never by passing source inline to an
  MCP `deploy_edge_function` call.** Four live functions were deployed that way and ended up
  with no source in any repo; recovering them is what PR #132 was for. Inline deploys also
  bypass the build check and the secret scan.
- **Deploy with `scripts/deploy-function.sh`, not a bare `supabase functions deploy`.** The
  bare command works from any full checkout, a linked worktree included, and will happily ship
  branch code to production; the script refuses unless you are in the canonical checkout, at
  the repo root, on `main`, level with `origin/main`, with the source committed. This was
  bypassed during PR #154 — three deploys went out from a worktree on a feature branch — which
  is exactly the failure mode the script exists to prevent, so prefer it even when the change
  itself looks safe.
- The deployed function named `server` is **owned by a different repo**
  (`DataAdmin/Spwebdatahandlingapp`, same project ref). Do not add a
  `supabase/functions/server/` directory here — deploying it would overwrite that project's
  live function.
- Read secrets from `Deno.env.get(...)`. Note that `gitleaks` will **not** catch a homemade
  shared password like `"orgname2026"` — it matches no provider format and no entropy rule.
  That class of secret has to be caught in review.
- A second copy of the intake handler used to sit at `src/supabase/functions/server/`
  (the original Figma Make scaffold layout). It was never a deploy path, nothing imported
  it, and its `make-server-535d8907` routes were never deployed — but it was being patched
  in parallel, so security fixes had to be written twice. Removed; see git history if the
  old `/impact/*` or `/volunteer` handlers are ever needed.

## Development Standards

- Never modify `main` directly.

- Keep changes scoped and reversible.
